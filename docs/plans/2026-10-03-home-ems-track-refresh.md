# 홈·EMS 노출 트랙 갱신

## 요청과 원인

- 사용자가 홈과 EMS 페이지에 노출되는 트랙 업데이트를 요청했다.
- 두 화면은 `ems_track_sections`에 저장된 에디토리얼 membership을 조회한다. 일반 수집 루틴은 이 membership을 자동으로 갱신하지 않는다.
- 기존 TIDAL 에디토리얼 동기화 명령으로 현재 카탈로그의 활성 트랙을 다시 연결한다. 장르를 추정해 배정하지 않는다.

## 작업 순서와 경계

1. 운영 화면/API·DB membership의 변경 전 상태와 독립 화면 설정을 기록한다.
2. 현재 운영 EMS 이미지로 제한된 TIDAL 조회와 dry-run을 실행한다. 실제 저장 전 모든 노출 섹션의 충족 여부를 확인한다.
3. 변경 대상 section과 membership의 복구 가능한 스냅샷을 저장소 밖 운영 artifact에 저장한다. 같은 후보 목록으로 guarded sync를 단일 transaction에서 실행한다.
4. 변경 후 DB, 홈·EMS 공개 API 및 실제 화면을 대조한다. 화면 설정·비대상 membership·사용자 데이터와 서비스 실행 상태를 보존한다.
5. 결과와 증거 경로를 변경 기록에 남긴다. 데이터 갱신이므로 이미지 재배포는 필요하지 않다.

## 완료 검증 기준

- C1: dry-run 쓰기 없음과 노출되는 5개 에디토리얼 섹션 각각 최소 6곡 확보. 기존 guarded gate 회귀 테스트 통과.
- C2: 실제 membership 갱신, 변경된 트랙 ID의 재현 가능한 비교, 섹션별 최대 12곡·전역 중복 0·활성 및 최신 KR STREAM 재생 가능 조건 충족. 복구 스냅샷 읽기 확인.
- C3: 홈(3개)과 EMS(5개) 공개 API HTTP 200 및 DB 목록과 일치. 실제 홈·EMS 화면의 최신 목록 표시 확인.
- C4: 독립 화면 설정·비대상 membership·사용자 데이터 보존 및 Web/EMS 서비스 재시작 없이 readiness HTTP 200.

## 실패 처리

- 원본 조회나 join 기준이 충족되지 않으면 운영 membership을 교체하지 않는다.
- 첫 전체 검증에서 FAIL/UNVERIFIED 합계가 3개 이상이면 개별 증상 수정을 멈추고 최초 실패 계층을 보고한다. 2개 이하이면 원인을 수정하고 전체 검증을 다시 실행한다.
- 개인 데이터 및 전체 DB를 복원하는 방식은 사용하지 않는다. section 단위 변경 전 스냅샷을 복구 근거로 보존한다.

## 실행 결과

- C1~C4 모두 PASS. 기존 회귀 테스트 11개, 운영 dry-run·실제 sync·DB/API·로그인 브라우저 대조를 완료했다.
- 홈 36곡 중 신규 ID 7개, EMS 60곡 중 신규 ID 11개를 반영했다. 5개 섹션은 각 12곡을 유지한다.
- 세부 증거와 검증 범위는 `docs/changes/2026-10-03-home-ems-track-refresh.md`에 기록했다.
