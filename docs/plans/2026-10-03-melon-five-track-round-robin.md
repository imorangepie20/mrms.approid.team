# 멜론 5곡 묶음·장르 순환

## 요청과 원인

사용자가 100곡 묶음을 5곡으로 줄이고 발라드 외 장르도 수집하도록 요청했다. 기존 `melon.py`는 한 장르의 모든 페이지를 처리해야 다음 장르로 넘어간다. 운영 원천 장르는 발라드 12,493곡뿐이며 열린 작업은 발견 0곡인 pending 작업 하나다. 멜론 paging endpoint의 `pageSize=5` 요청은 실제 HTTP 200·파싱 5곡을 확인했다.

## 변경 순서

1. 재현·회귀 테스트로 5곡 요청, 8장르 순환, 독립 커서, 종료 장르 건너뛰기, 중복 페이지 차단, 기존 묶음 처리 경계를 확인한다.
2. migration `032_melon_genre_checkpoints`로 장르별 JSON 체크포인트를 추가하고 기존 순차 진행 위치를 보존한다. 기존 100곡 묶음은 먼저 처리하므로 과거 count 제약은 유지한다.
3. 워커가 한 장르에서 최대 5곡을 저장한 뒤 다음 미완료 장르로 순환하도록 변경한다. 후보 처리 후 60초 대기, 요청 간격·429·KR 매칭 정책은 유지한다. URL 수동 수집의 기본 50곡 페이지는 유지한다.
   운영에서 TIDAL 관리자 작업 running 1개가 전체 처리 루프를 점유하고 멜론 pending 작업이 실행되지 않는 것도 확인했다. `admin_ingestion.py`의 TIDAL 후보 처리 사이에 실행 가능한 멜론 작업 한 tick을 처리해 기아 상태를 해소한다. 멜론 pause·다음 묶음 시각·TIDAL retry 시각은 존중한다.
4. 관리자 안내를 5곡·장르 순환으로 맞추고 운영 런북을 갱신한다.
5. 검증한 기능을 커밋·푸시하고 Web·EMS 이미지에 적용한다. DB backup 검증 후 migration을 적용하고 기존 열린 작업을 이어간다. 장애 시 체크포인트를 보존하고 멜론 작업을 일시정지한 상태로 이전 이미지를 복구한다. 운영 down migration은 하지 않는다.

## 완료 기준과 객관적 검증

- V1: 5곡 요청과 장르별 페이지 위치·8장르 순환·종료/중복/기존 묶음 회귀 pytest 통과.
- V2: 격리 PostgreSQL에서 migration apply/down/reapply 및 기존 작업 ID·누적 수·커서 보존, 실제 원천곡/장르/후보/체크포인트 transaction 검증.
- V3: EMS 전체 pytest, Web migration loader 회귀, 관리자·Web lint/build, `git diff --check` 통과. API 응답 계약은 변경하지 않는다.
- V4: 운영 backup 읽기·checksum, migration 032, Web/EMS source revision, healthy/restart 0, 공개 readiness 200 및 대상 외 서비스 보존 확인.
- V5: 운영 기존 작업이 5곡 묶음으로 진행하고 발라드 외 장르 관계를 저장함을 DB의 작업 ID·발견 수·장르별 체크포인트로 확인.

검증 결과와 실제 명령은 변경 기록에 남긴다. 전체 장르의 모든 페이지를 운영에서 끝까지 수집하는 것은 완료 기준에 포함하지 않는다.
