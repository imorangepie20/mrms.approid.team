# 갱신 때 같은 곡이 재선정되는 문제

## 원인과 수정 범위

- 기존 관리자는 원본 상위 12곡을 매번 결정적으로 선택한다. 원본이 같으면 추가/제외가 0인 미리보기가 재생성된다.
- 관리자 갱신만 현재 홈·EMS 공통 선곡에 없는 후보를 먼저 선택한다. 이 두 그룹 안에서는 기존 TIDAL 원본 순위를 유지하고, 새 후보가 부족하면 기존 곡으로 12곡까지 채운다.
- 제목이나 아티스트로 장르를 추정하지 않는다. 활성/최신 KR STREAM/30초 조건, 섹션 간 중복 제거, 원본 provenance와 5개 섹션 최소 6곡, 미리보기/확인/transaction 경계를 유지한다.
- 현재 노출만 피하므로 과거 노출된 곡이 이후 다시 등장할 수 있다. 후보가 전혀 없으면 같은 곡이 남으며 화면에 이를 설명한다. 영구 제외나 개인화 규칙은 추가하지 않는다.
- 후보 선택 후 화면 순위를 0부터 다시 부여한다. 기존 CLI의 순위 기반 갱신은 그대로 유지한다.
- Python 회귀 → 관리자 문구/추가·제외 합계 → 격리 DB와 앱 빌드 → 커밋/푸시/운영 Web·EMS 교체 → 실제 새 미리보기와 공개 선곡 적용 순서로 진행한다. source-routines·개인 데이터·화면 설정은 보존한다.

## 객관적 검증 기준

- C1: 수정 전 동일 후보/현재 목록으로 같은 곡이 선택되는 재현 테스트가 실패한다. 수정 후 미노출 우선, 후보 부족 채움, 전부 기존 후보, ISRC 연결, 전역 중복 제거와 CLI 기존 순위 회귀가 통과한다.
- C2: Python 전체 및 관련 Web/Admin 테스트, lint·타입/production build, 실제 PostgreSQL preview/apply 회귀와 diff check가 통과한다. UI 문구가 현재 노출 회피/후보 부족을 명시하고 결과 순서와 일치한다.
- C3: 운영 이미지 revision/readiness와 로그인 관리자 미리보기에서 실제 추가곡 >0을 확인한다. 저장 미리보기와 적용 후 공개 홈/EMS ID/순서가 일치하고 기존 대비 변경 >0, 개인 데이터·독립 설정·비대상 membership·source-routines 보존과 Melon heartbeat 진전을 확인한다.

첫 전체 검증에서 비통과 체크가 3개 이상이면 최초 실패 계층을 보고하고 증상 수정을 중단한다. 2개 이하이면 원인 수정 후 전체 기준을 재검증한다.

## 결과

- C1~C3 모두 PASS. 기능 `3cd1ea3`을 운영에 배포하고 실제 관리자 확인 버튼으로 홈 29곡·EMS 52곡을 교체했다.
- 동일 후보 재선정 red 재현, 22개 선곡 회귀, Python 116개·Web 41개·Admin 13개, 격리 DB 11개 assertion, 두 앱 lint/build와 운영 보존·실제 카드 순서 검증을 통과했다.
- 첫 HTTP 검사 일회성 520 후 내부/공개 200과 전체 운영 검증을 재확인했다. 정확한 응답 원인은 확정하지 않았다. 상세 증거와 범위 밖 미검증은 `docs/changes/2026-10-03-editorial-refresh-variety.md`에 기록한다.
