# 사용자 좋아요 기능 설계

## 목적

검색·GMS·EMS에서 노출하는 TIDAL 트랙, 플레이리스트, 앨범, 아티스트에 사용자별 좋아요 기능을 제공한다. 좋아요는 기존 플레이리스트 가져오기, MMS 저장 트랙, GMS 추천 수락·싫어요와 분리해 저장한다.

MMS에서는 기존 `저장한 트랙` 영역을 제거하고 다음 순서로 가져온 컬렉션과 개인 좋아요 컬렉션을 표시한다.

1. 가져온 플레이리스트
2. 좋아요한 트랙
3. 좋아요한 플레이리스트
4. 좋아요한 앨범
5. 좋아요한 아티스트

## 확정된 제품 규칙

- 좋아요 대상은 `track`, `playlist`, `album`, `artist` 네 종류다.
- 각 종류의 좋아요는 독립적이다. 플레이리스트나 앨범 좋아요가 내부 트랙 좋아요를 자동으로 만들지 않는다.
- 현재 가져온 트랙과 플레이리스트는 자동으로 좋아요 처리하지 않는다.
- 좋아요 해제는 좋아요 레코드만 삭제한다. 가져온 플레이리스트, 트랙, 검색 결과나 추천 상태는 삭제하거나 변경하지 않는다.
- GMS의 기존 추천 수락·싫어요는 추천 학습을 위한 별도 동작으로 유지한다.
- 로그인하지 않은 사용자에게도 하트 버튼은 표시한다. 클릭하면 `/api/auth/login?returnTo=...`로 이동하며, 로그인 전 클릭한 항목을 자동으로 좋아요 처리하지 않는다.
- MMS는 상단에 트랙, 플레이리스트, 앨범, 아티스트 좋아요 개수 박스를 표시한다.

## 데이터 모델

### `user_likes`

하나의 통합 테이블에 모든 좋아요 유형을 저장한다.

| 열 | 의미 |
| --- | --- |
| `id` | 내부 UUID 기본 키 |
| `user_id` | `app_users.id` 외래 키 |
| `entity_type` | `track`, `playlist`, `album`, `artist` 중 하나 |
| `source` | `tidal`, `catalog` 등 항목의 출처 |
| `source_id` | 해당 출처 안에서 안정적인 리소스 ID |
| `title` | 화면 표시용 이름 또는 제목 |
| `subtitle` | 아티스트, 큐레이터 등 보조 표시 문자열 |
| `artwork_url` | 화면 표시용 이미지 URL, 없으면 `NULL` |
| `metadata` | 유형별 추가 표시·재생 정보를 담는 JSONB |
| `created_at` | 좋아요 시각 |

`UNIQUE (user_id, entity_type, source, source_id)`로 중복 좋아요를 막는다. TIDAL 검색·가져오기 항목은 `source=tidal`과 TIDAL 리소스 ID를 사용한다. 현재 EMS/GMS의 내부 카탈로그처럼 TIDAL ID가 없는 항목은 `source=catalog`와 기존의 안정적인 항목 ID를 사용한다. 모든 조회·삽입·삭제는 Auth0 subject로 찾은 현재 `app_users.id`에 한정한다.

`metadata`에는 MMS가 외부 재검색 없이 항목을 렌더링하고 재생·상세 진입하는 데 필요한 최소 스냅샷만 저장한다.

- 트랙: 앨범명, duration, playback availability 등 기존 `Track` 구성에 필요한 값
- 플레이리스트: 큐레이터, track count
- 앨범: 아티스트명, release date 등 현재 검색 카드가 사용하는 값
- 아티스트: 현재 검색 응답에서 제공하는 표시 정보

서버는 `entity_type`별 입력 스키마를 검증하며 임의의 대형 JSON이나 알 수 없는 필드는 저장하지 않는다. 스냅샷은 좋아요 시점 표시 정보이며 TIDAL 원본의 최종 상태를 확정하는 데이터로 취급하지 않는다.

마이그레이션은 `005_user_likes.sql`과 대응하는 rollback 파일을 추가한다. 기존 데이터는 변환하지 않고 좋아요는 빈 상태에서 시작한다.

## 서버 API와 데이터 흐름

### 조회

`GET /api/likes`는 로그인한 사용자의 좋아요 전체를 반환한다. 선택적인 `type` 필터는 네 유형 중 하나만 허용한다. 응답은 유형별 배열과 개수를 포함해 클라이언트 초기화와 MMS 렌더링에 함께 사용할 수 있게 한다.

서버 root layout은 현재 사용자의 좋아요를 한 번 조회해 전역 좋아요 상태의 초기값으로 전달한다. MMS는 같은 전역 상태를 좋아요 표시 소스로 사용하며 별도 중복 조회하지 않는다. 기존 `getSavedTracks()` 기반 저장 트랙 목록은 MMS 표시 입력에서 제거하되, `getSavedPlaylists()`와 `getSavedPlaylistTracks()`로 가져온 플레이리스트 카드와 저장된 수록곡 상세를 계속 제공한다.

### 추가

`PUT /api/likes/{entityType}/{source}/{sourceId}`는 검증된 표시 스냅샷을 받아 upsert한다. 같은 항목의 반복 요청은 성공하며 레코드를 중복 생성하지 않는다. 경로의 유형, 출처와 ID를 신뢰 경계에서 검증한다.

### 해제

`DELETE /api/likes/{entityType}/{source}/{sourceId}`는 현재 사용자의 일치 레코드만 삭제한다. 이미 없는 항목도 성공으로 처리해 반복 요청에 안전하게 만든다.

### 인증·오류

- 비로그인 API 요청은 `{ "code": "unauthorized" }`, HTTP `401`을 반환한다.
- 잘못된 유형, ID 또는 스냅샷은 안정적인 오류 코드와 HTTP `400`을 반환한다.
- DB 오류는 내부 세부 정보 없이 HTTP `500`으로 응답한다.
- 다른 사용자의 좋아요 존재 여부는 응답으로 노출하지 않는다.

## 클라이언트 구조

### 좋아요 상태

앱 전역에 좋아요 상태 공급자를 두고 로그인 사용자의 좋아요를 한 번 불러온다. 식별 키는 `${entityType}:${source}:${sourceId}`다. 공통 훅은 다음 기능을 제공한다.

- 현재 좋아요 여부 조회
- 좋아요 추가·해제
- 유형별 항목 및 개수 조회
- 요청 중 중복 클릭 방지
- 실패 시 이전 상태 복구와 사용자 오류 표시

좋아요 클릭은 낙관적으로 하트 상태를 변경한다. 서버 요청이 실패하면 직전 상태로 복구한다. 같은 항목의 요청이 진행 중일 때는 버튼을 잠시 비활성화한다.

### 공통 하트 버튼

공통 `LikeButton`은 유형과 검증 가능한 스냅샷을 입력으로 받는다.

- 빈 하트: `좋아요 {항목명}`
- 채워진 하트: `좋아요 취소 {항목명}`
- 키보드 포커스와 충분한 클릭 영역 제공
- 색상만으로 상태를 구분하지 않고 `aria-pressed`를 함께 사용
- 비로그인 클릭 시 현재 경로를 `returnTo`로 전달해 로그인 이동

### 화면별 적용

- 공통 `TrackList`: 모든 트랙 행 끝에 좋아요 열을 추가한다. 재생 불가 트랙도 좋아요할 수 있다.
- `TrackCard`: 기존 `담기`는 GMS 추천 수락 용도로 유지하고 별도 하트를 추가한다. 같은 화면에서 의미가 겹치지 않도록 기존 GMS 텍스트 버튼은 `추천 수락`으로 표현한다.
- 검색: 트랙 목록, 플레이리스트 카드, 앨범 카드, 아티스트 결과에 하트를 표시한다. 검색 결과에 아티스트 전용 표시가 부족하면 기존 응답의 아티스트 데이터를 이용한 카드/영역을 추가한다.
- EMS·GMS: 현재 실제로 노출되는 모든 트랙·플레이리스트·앨범·아티스트 컴포넌트에 공통 하트를 적용한다. 존재하지 않는 유형을 위해 가짜 섹션이나 데이터를 만들지는 않는다.

좋아요 버튼 클릭은 상위 카드 열기나 트랙 재생 이벤트로 전파되지 않게 한다.

## MMS 화면

페이지의 정체성과 최상위 제목은 `My Music Space`다. 좋아요는 페이지 자체의 이름이 아니라 가져온 플레이리스트와 함께 관리하는 부속 콘텐츠로 표현한다. 기존 `저장한 트랙` 제목, 검색·정렬 영역, 가져온 트랙 기반 목록을 제거하고 네 개의 좋아요 개수 박스를 보조 요약으로 표시한다.

본문은 다음 순서를 유지한다.

1. `가져온 플레이리스트`: 가져오기 때 DB에 저장한 수록곡으로 상세, 전체 재생·셔플을 제공하고 플레이리스트 자체의 좋아요 하트를 표시
2. `좋아요한 트랙`: 공통 `TrackList`를 사용해 재생 가능
3. `좋아요한 플레이리스트`: 카드 선택 시 TIDAL 상세 트랙 목록을 열고 전체 재생·셔플 지원
4. `좋아요한 앨범`: 카드 선택 시 TIDAL 상세 트랙 목록을 열고 전체 재생·셔플 지원
5. `좋아요한 아티스트`: 저장된 아티스트 정보 카드 표시

각 영역은 항목이 없어도 제목과 독립적인 빈 상태를 표시한다. MMS에서 하트를 해제하면 해당 항목을 즉시 목록에서 제거하고 개수를 갱신한다. 플레이리스트·앨범 상세에서 해제한 경우 상세 화면을 닫고 해당 카드가 목록에서 사라지게 한다.

## 변경 범위와 비범위

### 포함

- 사용자별 좋아요 DB와 조회·추가·해제 API
- 검색·GMS·EMS의 기존 음악 항목에 공통 하트 적용
- MMS의 `My Music Space` 정체성을 유지한 컬렉션 화면 재구성
- 가져온 TIDAL 플레이리스트 카드와 DB 수록곡 상세 유지
- 플레이리스트·앨범 좋아요 항목의 기존 TIDAL 상세 조회와 재생 연결
- 관련 단위·통합 테스트와 한국어 변경 기록

### 제외

- TIDAL 계정 자체의 favorites와 동기화
- 가져온 데이터의 자동 좋아요 마이그레이션
- 플레이리스트/앨범 좋아요 시 수록곡 일괄 좋아요
- 아티스트 상세 페이지나 아티스트 라디오 신규 구현
- 추천 모델이 좋아요를 학습 입력으로 사용하는 변경

## 검증 기준

1. DB 테스트에서 사용자 격리, 유형별 조회, 중복 upsert, 사용자 범위 삭제를 확인한다.
2. API 테스트에서 정상 조회·추가·해제, 반복 요청, 비로그인 `401`, 잘못된 입력 `400`을 확인한다.
3. 공통 UI 테스트에서 빈/채운 하트, `aria-pressed`, 로그인 이동, 낙관적 변경, 실패 복구, 이벤트 전파 차단을 확인한다.
4. 검색·GMS·EMS 테스트에서 실제 노출되는 모든 지원 유형에 하트가 표시되는지 확인한다.
5. MMS 테스트에서 저장 트랙 영역은 사라지고 가져온 플레이리스트가 네 좋아요 영역보다 먼저 표시되는지 확인한다.
6. 가져온 플레이리스트와 좋아요한 트랙·플레이리스트·앨범 상세 재생이 기존 플레이어 큐를 올바르게 구성하는지 확인한다.
7. GMS 추천 수락·싫어요와 새 좋아요 상태가 서로 변경되지 않는지 확인한다.
8. 관련 테스트, 전체 테스트, lint, production build를 순서대로 실행하고 실제 성공한 결과만 변경 기록에 남긴다.
