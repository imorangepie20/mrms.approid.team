# MMS 내부 플레이리스트 관리 설계

## 목적

인증된 사용자가 My Music Space(MMS)에서 music-pie 내부 플레이리스트를 만들고, 이름과 설명을 수정하고, 삭제할 수 있게 한다. 검색·EMS·GMS·MMS 등 트랙을 표시하는 화면에서는 사용자가 원하는 트랙을 자신의 내부 플레이리스트에 추가할 수 있다. 플레이리스트 상세에서는 트랙을 제거하고 순서를 바꾸며 기존 전역 플레이어로 전체 재생하거나 셔플할 수 있다.

이 기능은 music-pie 내부 데이터만 변경한다. 가져온 TIDAL 플레이리스트와 TIDAL 원격 계정, EMS 원본 카탈로그, 좋아요, 다른 사용자의 데이터는 변경하지 않는다.

## 확정 범위

- MMS 내부 플레이리스트 생성, 목록 조회, 상세 조회, 이름·설명 수정, 삭제
- 검색·EMS·GMS·MMS를 포함한 트랙 UI에서 내부 플레이리스트 선택 및 트랙 추가
- 트랙 추가 대화상자 안에서 새 플레이리스트 생성
- 플레이리스트 상세에서 트랙 제거와 위·아래 순서 이동
- 플레이리스트 전체 재생과 셔플
- 플레이리스트별 동일 트랙 중복 방지
- 사용자 소유권과 인증 경계 검증
- 데스크톱·모바일·키보드 조작 지원

## 범위 밖

- TIDAL 원격 플레이리스트 생성·수정·삭제
- 가져온 TIDAL 플레이리스트의 이름·설명·수록곡 변경
- EMS 원본 카탈로그나 좋아요 데이터 삭제
- 공동 편집, 공유 링크, 공개 플레이리스트
- 자동 추천 트랙 삽입
- 드래그 앤 드롭 정렬
- 커버 이미지 업로드
- 운영 DB migration 적용과 운영 배포

## 데이터 모델

기존 `user_playlists`와 `user_playlist_tracks`는 TIDAL에서 가져온 스냅샷의 소유권과 동기화 의미를 가진다. 내부 플레이리스트를 이 테이블에 섞지 않고 신규 테이블로 분리한다.

### `mms_playlists`

| 열 | 타입 | 의미 |
| --- | --- | --- |
| `id` | UUID PK | 내부 플레이리스트 ID |
| `user_id` | UUID FK | `app_users.id` 소유 사용자 |
| `name` | TEXT | 공백 제거 후 1~100자의 표시 이름 |
| `description` | TEXT NULL | 공백 제거 후 최대 500자의 설명 |
| `created_at` | TIMESTAMPTZ | 생성 시각 |
| `updated_at` | TIMESTAMPTZ | 마지막 변경 시각 |

사용자 삭제 시 플레이리스트가 함께 삭제되도록 `user_id`에 `ON DELETE CASCADE`를 적용한다. 사용자별 최신 수정 순서 조회를 위한 인덱스를 둔다. 같은 사용자가 같은 이름의 플레이리스트를 여러 개 만드는 것은 허용한다.

### `mms_playlist_tracks`

| 열 | 타입 | 의미 |
| --- | --- | --- |
| `id` | UUID PK | 플레이리스트 항목 ID |
| `playlist_id` | UUID FK | `mms_playlists.id` |
| `track_key` | TEXT | 플레이리스트 안의 중복 판정 키 |
| `source` | TEXT | 트랙을 추가한 출처 |
| `source_id` | TEXT | 출처의 트랙 ID |
| `tidal_track_id` | TEXT NULL | 재생 가능한 TIDAL 트랙 ID |
| `title` | TEXT | 추가 시점 제목 스냅샷 |
| `artist` | TEXT | 추가 시점 아티스트 스냅샷 |
| `album` | TEXT | 추가 시점 앨범 스냅샷 |
| `artwork_url` | TEXT NULL | 앨범 아트 참조 |
| `duration_seconds` | INTEGER NULL | 재생 시간 |
| `playback_available` | BOOLEAN | 추가 시점 재생 가능 여부 |
| `position` | INTEGER | 0부터 시작하는 표시·재생 순서 |
| `created_at` | TIMESTAMPTZ | 추가 시각 |

TIDAL ID가 있으면 `track_key`는 `tidal:{tidalTrackId}`다. 없으면 `{source}:{sourceId}`를 사용한다. `(playlist_id, track_key)`를 고유 키로 두어 출처 화면이 달라도 같은 TIDAL 트랙의 중복을 막는다. `(playlist_id, position)`도 고유하게 유지한다. 플레이리스트 삭제 시 항목만 `ON DELETE CASCADE`로 제거하며 원본 데이터는 유지한다.

## 서버 경계

모든 DB 함수는 Auth0 `sub`를 받아 `app_users.id`와 플레이리스트 소유권을 함께 확인한다. ID만으로 플레이리스트를 변경하지 않는다. 다른 사용자 소유 ID는 존재하지 않는 것처럼 처리한다.

### API

- `GET /api/mms/playlists`: 현재 사용자의 내부 플레이리스트 요약 목록
- `POST /api/mms/playlists`: 이름과 선택적 설명으로 생성
- `GET /api/mms/playlists/{playlistId}`: 메타데이터와 순서가 적용된 트랙 상세
- `PATCH /api/mms/playlists/{playlistId}`: 이름과 설명 수정
- `DELETE /api/mms/playlists/{playlistId}`: 내부 플레이리스트와 그 항목 삭제
- `POST /api/mms/playlists/{playlistId}/tracks`: 검증된 트랙 스냅샷을 마지막 순서에 추가
- `DELETE /api/mms/playlists/{playlistId}/tracks/{itemId}`: 항목 제거 후 순서를 연속 값으로 정규화
- `PATCH /api/mms/playlists/{playlistId}/tracks/reorder`: 전체 항목 ID 배열로 순서 변경

트랙 추가 payload는 화면의 전체 `Track` 객체를 그대로 신뢰하지 않는다. 허용한 필드만 파싱하고 문자열 길이, 숫자 범위, URL 형식, `source`, ID를 검증한다. 재생 가능 트랙은 `tidalTrackId`를 유지하며 재생 불가 트랙도 컬렉션에는 보관할 수 있다.

정렬 API는 현재 플레이리스트 항목 ID 전체가 중복 없이 정확히 한 번씩 전달된 경우에만 처리한다. `CASE` 기반 update 또는 안전한 임시 position을 사용하는 하나의 트랜잭션으로 고유 순서 충돌 없이 반영한다.

### 오류 계약

| 상태 | 코드 예시 | 조건 |
| --- | --- | --- |
| `400` | `invalid_playlist_name`, `invalid_track`, `invalid_track_order` | 입력 검증 실패 |
| `401` | `unauthorized` | Auth0 세션 없음 |
| `404` | `playlist_not_found`, `playlist_track_not_found` | 없거나 다른 사용자 소유 |
| `409` | `playlist_track_already_exists` | 같은 트랙 중복 추가 |
| `500` | `playlist_read_failed`, `playlist_write_failed` | 예기치 않은 서버·DB 오류 |

오류 응답에는 외부 응답 본문, 토큰, SQL 상세를 포함하지 않는다.

## 사용자 화면

### MMS 목록

가져온 TIDAL 플레이리스트와 구분되는 `내 플레이리스트` 섹션을 MMS 상단에 둔다. 섹션 머리글의 `새 플레이리스트` 버튼은 이름과 설명 입력 대화상자를 연다. 카드는 이름, 트랙 수, 최근 수정 상태를 표시하며 선택하면 상세로 이동한다.

빈 상태에서는 기능 설명과 생성 버튼을 함께 제공한다. 연결이 해제되어도 내부 플레이리스트는 그대로 조회·관리할 수 있다.

### 플레이리스트 상세

상세 화면은 이름, 설명, 트랙 수, 전체 재생, 셔플, 편집, 삭제를 제공한다. 편집은 이름과 설명만 변경한다. 삭제 확인에는 플레이리스트 이름과 원본 음악·가져온 데이터가 삭제되지 않는다는 문구를 표시한다.

트랙 행은 재생과 좋아요 외에 이 플레이리스트에서 제거, 위로 이동, 아래로 이동을 제공한다. 첫 항목의 위 이동과 마지막 항목의 아래 이동은 비활성화한다. 드래그 없이 버튼과 명확한 접근성 이름으로 모바일·키보드 조작을 지원한다.

### 모든 트랙 화면의 추가 메뉴

공통 `TrackList`, 트랙 카드, GMS 전용 트랙 행에 `플레이리스트에 추가` 진입점을 제공한다. 대화상자는 현재 사용자의 내부 플레이리스트와 해당 트랙의 포함 여부를 표시한다. 사용자는 기존 플레이리스트를 선택하거나 대화상자 안에서 새 플레이리스트를 만든 뒤 곧바로 트랙을 추가할 수 있다.

비로그인 사용자가 진입하면 로그인 필요 안내를 표시한다. 추가 중에는 중복 제출을 막고, 성공하면 포함 상태와 트랙 수를 즉시 갱신한다. `409`는 일반 실패가 아니라 `이미 추가된 트랙입니다`로 안내한다.

## 상태와 일관성

- 생성·수정·삭제·트랙 변경 성공 후 관련 클라이언트 상태를 서버 응답으로 갱신한다.
- 실패 시 기존 목록과 상세 상태를 유지하고 대화상자 안에 재시도 가능한 오류를 표시한다.
- 트랙 제거와 순서 이동은 서버 성공 후 화면에 확정한다. 요청 중 같은 항목의 반복 동작을 막는다.
- TIDAL 원격 API에는 쓰기 요청을 보내지 않는다.
- 내부 플레이리스트 변경은 가져온 라이브러리의 취향 분석 입력이나 좋아요 상태를 자동으로 변경하지 않는다.

## 접근성·반응형 기준

- 대화상자는 제목, 닫기 버튼, 포커스 이동과 Escape 닫기를 제공한다.
- 아이콘 전용 동작에는 트랙과 행동을 포함한 접근성 이름을 둔다.
- 최소 터치 영역을 기존 UI 기준에 맞춘다.
- 좁은 화면에서는 메타데이터보다 핵심 행동을 우선하고 트랙 관리 버튼을 줄바꿈한다.
- 저장·오류 메시지는 적절한 `role="status"` 또는 `role="alert"`로 전달한다.

## 검증 기준

### Migration·DB

- 신규 테이블, FK, cascade, 중복·순서 unique constraint, 인덱스를 확인한다.
- 다른 사용자의 플레이리스트를 조회·수정·삭제·항목 변경할 수 없다.
- 중복 트랙 추가가 거부된다.
- 제거 후 position이 연속으로 정규화된다.
- 잘못된 전체 순서는 아무 변경 없이 거부된다.
- 플레이리스트 삭제가 가져온 TIDAL 데이터와 EMS 원본에 영향을 주지 않는다.

### API

- 인증 없음 `401`, 입력 오류 `400`, 소유권 불일치 `404`, 중복 `409`를 검증한다.
- 생성·수정·삭제와 트랙 추가·제거·재정렬의 정상 응답을 검증한다.
- 서버 오류가 안정적인 공개 오류 코드로 변환되는지 확인한다.

### UI

- MMS에서 생성, 이름·설명 수정, 삭제 확인과 즉시 목록 반영을 검증한다.
- 트랙 메뉴에서 목록 선택, 인라인 생성, 중복 안내를 검증한다.
- 상세의 제거와 위·아래 이동, 전체 재생, 셔플을 검증한다.
- 비로그인 안내, 빈 상태, 요청 중 비활성화, 오류 재시도를 검증한다.
- 가져온 TIDAL 플레이리스트 UI가 기존대로 조회·재생되는지 회귀 검증한다.

### 실행 검증

1. 관련 Vitest를 먼저 실행한다.
2. `npm test`
3. `npm run lint`
4. `npm run build`
5. 저장소 루트에서 `git diff --check`

실제 성공한 명령만 완료 기록에 포함한다. 운영 DB migration과 배포는 별도 승인과 절차가 있을 때만 수행한다.

## 완료 기준

- 인증된 사용자가 내부 플레이리스트를 생성·수정·삭제할 수 있다.
- 모든 주요 트랙 표시 흐름에서 내부 플레이리스트로 트랙을 추가할 수 있다.
- 상세에서 트랙을 제거하고 순서를 변경하며 해당 순서로 재생할 수 있다.
- 중복, 인증, 사용자 격리, 삭제 경계가 DB·API·UI 테스트로 고정된다.
- TIDAL 원격 데이터와 기존 가져온 라이브러리·EMS·좋아요에 쓰기 부작용이 없다.
- 관련 테스트, 전체 테스트, lint, build, diff 검사가 성공한다.
