# GMS 추천 언어·장르 반영 설계

작성일: 2026-10-29

## 1. 배경과 목적

사용자 보고: "내 플레이리스트는 주로 영어인데 다른 언어가 너무 많이 추천되고, 트로트는 한 곡도 없는데 그것도 추천된다."

2026-10-29 운영 DB 읽기 전용 조회(`8534d93b-0828-442a-9795-d5f0d4bcf8dd`, 선택 플레이리스트 6개)로 확인한 사실:

- MMS 464곡은 재즈 중심(MusicBrainz 장르 상위 jazz·vocal jazz·cool jazz·hard bop·post-bop)이고, 문자 기준 라틴 425·한글 36·한자 3곡이다.
- 최근 노출 40곡은 폴란드어·포르투갈어(파두)·독일어·프랑스어 샹송·스페인어·터키어·중국어·트로트가 섞여 있고 재즈는 거의 없다. 다른 언어의 대부분은 **라틴 문자 유럽 언어**라 문자 판별만으로는 잡히지 않는다.
- 멜론 출처 EMS 곡의 트로트 비율은 650/6006(11%)인데, 이 사용자에게 노출된 멜론 출처 16곡 중 9곡이 트로트다("한잔해", "눈물강", "내 사랑 소래포구" 등).
- 한글 곡 판정 8건은 모두 reject다.
- 9/29 이후 노출 180곡이 모두 `baseline`이다. `hybrid-v0`는 9/29의 8곡뿐이다.

원인:

1. `baseline` 순위는 EMS 텍스트 임베딩(`제목 | 아티스트 | 앨범`, [embedding.py:13](../../../services/ems-pipeline/src/ems_pipeline/embedding.py))과 사용자 centroid의 유사도가 65%를 차지한다. 모델 `paraphrase-multilingual-mpnet-base-v2`는 언어가 달라도 의미가 같으면 가깝게 놓도록 학습됐다. 그래서 "사랑·눈물" 같은 제목 의미가 언어·장르와 무관하게 재즈 스탠더드와 가깝게 잡힌다.
2. 점수식과 후보 필터에 언어·장르 항목이 없다([gms.ts](../../../apps/web/src/lib/recommendations/gms.ts), [gms-recommendations.ts](../../../apps/web/src/lib/db/gms-recommendations.ts)).
3. 메타데이터가 비어 있다.
   - 활성 EMS 167,709곡 중 `mb_tags`가 있는 곡은 24,837(15%)이고, 아티스트 장르 캐시가 있는 곡은 614곡이다.
   - 사용자 MMS 중 `mb_genres`가 있는 곡은 49/464다.
   - 언어 정보는 없다. ISRC 국가 코드는 유통사 국가라 언어 근거로 쓸 수 없다. 예를 들어 MMS의 KR ISRC는 90곡인데 한글 곡은 36곡이다.

목적: 사용자 취향에 거의 없는 언어·장르가 추천 상위를 차지하지 않게 한다.

## 2. 목표·비목표·실패 조건

목표

- 사용자 MMS에 드물거나 없는 언어·장르의 후보는 **순위를 크게 낮춘다. 막지는 않는다.** 이는 사용자 결정이다.
- 취향이 고정되지 않도록 **배치에 탐색용 자리를 둔다**(사용자 결정). 낯선 언어·장르는 일반 자리에서는 감점으로 밀려나고, 탐색 자리에서만 의도적으로 노출된다.
- GMS 기본 배치 크기를 **12곡에서 24곡으로 늘린다**(사용자 결정). `DEFAULT_BATCH_SIZE`([gms-recommendation-batches.ts:14](../../../apps/web/src/lib/db/gms-recommendation-batches.ts)), 상한 `MAX_BATCH_SIZE`=24는 이미 있다.
- 언어·장르 판단 근거를 곡마다 추적 가능하게 저장한다(AGENTS 도메인 원칙).
- 현재 실제로 서빙 중인 `baseline` 경로에 먼저 적용한다.

비목표

- `hybrid-v0` 점수식 변경(같은 신호를 나중에 재사용할 수 있게만 설계한다).
- 하드 필터, 사용자가 직접 언어를 고르는 설정 UI.
- 가사 수집, 곡 단위 외부 API 호출, 임베딩 모델 교체.

실패로 보는 경우(동작은 하더라도)

- 언어·장르를 판단하지 못한 곡(unknown)이 크게 깎여서 신규·소수 아티스트가 사실상 사라진다.
- 한국어·트로트를 즐기는 다른 사용자의 추천이 나빠진다. 감점은 사용자별 분포 기준이어야 하고 전역 규칙이면 안 된다.
- 다른 사용자의 데이터가 섞인다. 공용인 아티스트·곡 속성은 괜찮지만, 사용자별 분포는 그 사용자의 데이터로만 계산한다.

## 4. 설계

### 4.1 공용 속성 (사용자 비종속)

- **장르 버킷 분류표**: 원시 태그(MB·Last.fm·멜론 장르명)를 상위 버킷 약 20~30개로 매핑하는 버전 관리 파일이다. 예: jazz, trot, k-ballad, k-pop, k-indie, chanson, fado, latin, schlager, classical, rock, hip-hop, r&b-soul, electronic, folk, country, pop.
  - 매핑에 없는 태그는 버린다. 기존 화이트리스트 결정([2026-09-21 genre-embedding-input](../../changes/2026-09-21-genre-embedding-input.md))과 같은 방향이다.
  - 분류표 버전을 저장 행에 남긴다.
- **아티스트 속성**: 정규화한 아티스트 이름(그리고 MB artist MBID가 있으면 MBID)을 키로, 장르 버킷 가중치와 언어 가중치, 출처별 원시 태그, 수집 시각, 분류표 버전을 저장한다. 출처는 MB 아티스트 태그와 Last.fm이다.
- **곡 속성**: EMS 곡과 사용자 `music_tracks` 양쪽에 대해 `language`(ISO 639-3 또는 `unknown`), `language_source`, 장르 버킷 가중치, `genre_source`를 둔다.
  - 언어 우선순위: MB 릴리스 언어(해당 recording이 실린 릴리스들의 최빈값, `zxx`·`mul` 제외) → Last.fm 언어·지역 태그 → 문자 판별 → `unknown`.
  - 장르 우선순위: 멜론 장르(멜론 출처 곡) → MB recording/release group 태그 → 아티스트 속성 → 없음.
- 수집과 계산은 모두 `ems-pipeline` 명령과 루틴에서 한다. Web 요청 경로에서는 외부 호출을 하지 않는다(CLAUDE.md TIDAL 호출 경계와 같은 원칙).
- 사용자 곡(`music_tracks`)도 같은 파이프라인 명령이 대상으로 삼는다. 사용자 곡은 `mb_recording_id`가 있으면 그것을 쓰고, 없으면 아티스트 속성과 문자 판별만 쓴다.

### 4.2 사용자 분포 (사용자별)

- 해당 사용자의 선택된 MMS 플레이리스트 곡과 accept한 추천 곡으로 언어 분포와 장르 버킷 분포를 만든다. `unknown`은 분포 계산에서 제외한다.
- reject한 곡은 해당 언어·장르의 가중치를 낮추는 근거로 쓴다. 단, reject가 그 언어·장르 전체를 0으로 만들지는 않는다.
- 다른 사용자의 데이터는 섞지 않는다.
- 분포는 취향 프로필 계산 시 함께 저장해서 추적할 수 있게 한다.

### 4.3 점수 반영 (`baseline`)

- 후보마다 언어 적합도(사용자 언어 분포에서 그 언어의 비중)와 장르 적합도(후보 장르 버킷과 사용자 장르 분포의 겹침)를 0~1로 계산한다.
- 기존 `calculateEmsScore` 결과에 하한이 있는 배수 감점을 곱한다. 비중이 충분히 높은 언어·장르는 감점이 없고, 비중이 0이면 하한까지 깎인다. 하한은 0보다 크게 둔다(차단 금지).
- `unknown`은 중립에 가깝게 둔다. 감점이 없거나 아주 작다.
- **후보 풀 문제**: 지금은 SQL이 텍스트 유사도 순으로 `min(120, limit×5)`개(기본 60개)를 먼저 자른다. 감점을 이 뒤에만 적용하면 풀이 이미 외국어 곡으로 차 있을 때 효과가 없다. 그래서 감점을 SQL의 풀 선정 단계에 반영하거나, 풀을 크게 늘린 뒤 감점하고 다시 자른다. 어느 쪽인지는 쿼리 비용을 측정해서 정한다.
- 이유 코드(`language_mismatch`, `genre_mismatch` 등)와 감점 값을 `score_components`에 기록한다.
- **탐색 자리**: 24곡 중 2곡(설계자 결정, 기존 "12곡 중 1곡" 비율 유지)을 탐색 자리로 둔다.
  - 감점 대상(언어 또는 장르 불일치)이면서 감점 전 점수가 높은 후보 중에서 고른다.
  - 같은 언어·장르가 두 탐색 자리를 함께 차지하지 않게 한다.
  - 이유 코드 `exploration`을 붙여 기록하고, 화면에는 일반 추천과 구분되는 짧은 표시를 단다.
  - 배치는 기존처럼 한 번 만들면 고정한다. 탐색 곡 선택은 배치 ID 기준으로 재현할 수 있게 한다.
  - 탐색 곡의 accept/reject도 4.2의 사용자 분포에 일반 곡과 같이 반영한다. 그래서 사용자가 탐색 곡을 좋아하면 그 언어·장르의 감점이 줄어든다.
  - 배치 크기가 24로 커지면 후보 풀은 `min(120, 24×5)` = 120이 된다. 4.3의 후보 풀 문제는 이 크기를 기준으로 측정한다.

### 4.4 표시

- 화면에 Last.fm 출처 표기와 링크를 추가한다(약관 2.7·4.2). 위치는 구현 시 기존 화면 패턴을 따른다.

## 5. 성공 기준

- 위 사용자로 운영 데이터 기준 오프라인 평가(읽기 전용)를 한다. 탐색 자리를 뺀 일반 22곡의 언어 분포가 MMS 분포에 가까워져야 하고, 트로트는 일반 자리에 나오지 않아야 한다. 탐색 자리는 별도로 집계한다.
- 같은 평가에서 한국어 곡이 많은 가상 분포를 넣으면 한국어 후보가 감점되지 않아야 한다.
- 커버리지 측정: 보강 후 활성 EMS 곡 중 언어가 `unknown`이 아닌 비율과 장르 버킷이 있는 비율을 기록한다. 이 수치는 구현 전에 덤프로 먼저 측정해서 목표치를 정한다.
- 기존 테스트와 lint·build 통과, 영구 제외(reject) 규칙 회귀 없음.

## 6. 제약

- 마이그레이션은 새 번호 파일과 `.down.sql` 짝으로 추가한다.
- Last.fm API 키는 사용자가 이미 발급했다. 서버 `shared/secrets/*.env`의 ems-pipeline용 파일에 `LASTFM_API_KEY`로 둔다. 저장소와 대화에 넣지 않는다.
- Last.fm 조회 대상에는 EMS 아티스트뿐 아니라 사용자 MMS에만 있는 아티스트도 포함한다(사용자 승인). 저장하는 것은 아티스트 이름과 태그뿐이고, 어느 사용자의 라이브러리에서 왔는지는 저장하지 않는다.
- Last.fm 저장 총량 100MB 이하, 태그 재수집 주기를 둔다. API 접근이 종료되면 데이터를 삭제할 수 있어야 한다(출처 컬럼으로 식별).
- MusicBrainz 덤프의 태그(derived)는 CC BY-NC-SA다. 비상업 용도라 사용할 수 있다.

## 7. 설계자 결정 (검토 후 확정, 사용자 확인 전)

- **랭킹 버전 분리**: 감점이 들어간 순위는 새 `ranking_version`(예: `baseline-v2`)으로 기록한다. 감점 전후의 결정이 같은 `baseline`으로 섞이지 않게 하기 위해서다. `ranking_version` CHECK 제약 변경은 새 마이그레이션으로 한다. 오프라인 평가를 통과하면 `GMS_RANKING_VERSION` 환경변수로 전체 적용하고, 문제가 생기면 기존 `baseline`으로 되돌린다. 실사용자가 소수라 allowlist·shadow 단계는 두지 않는다.
- **사용자 분포 계산 시점**: Web이 추천 요청 시 DB에서 계산한다. 대상은 MMS와 accept/reject 곡을 곡 속성 테이블과 조인한 결과다. 외부 호출은 없고, 사용자당 수백 행이라 비용이 작다. 계산된 분포와 분류표 버전은 노출 배치의 점수 기록에 남긴다. 이렇게 하면 파이프라인이 속성을 갱신하는 즉시 다음 추천부터 반영되고, 파이프라인이 사용자 프로필 테이블에 쓸 필요가 없다.
- **사용자 곡 언어 커버리지 부족 시**: `mb_recording_id`가 없는 사용자 곡은 MB 덤프 안에서 ISRC로 recording을 매칭해도 된다(외부 호출 없음). 그래도 이 사용자 MMS의 언어 판별률이 낮으면, 언어 감점을 빼고 장르 감점만으로 1단계를 진행할지 사용자에게 보고한 뒤 정한다.

## 8. 구현자에게 맡기는 것

- 테이블 이름과 컬럼 구성, 아티스트 이름 정규화 규칙.
- 장르 버킷 분류표의 정확한 목록과 매핑(위 예시는 출발점).
- 감점 함수의 정확한 모양과 상수(하한, 비중 임계치). 단, 성공 기준의 오프라인 평가로 정한다.
- MB 덤프에서 recording→release 언어를 뽑는 구체적인 조인 방식.
- 단계 분할과 배포 순서(수집 → 계산 → 점수 반영 → 표시).
