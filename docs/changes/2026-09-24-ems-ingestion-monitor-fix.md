# EMS 수집 모니터링 정합성 수정

## 이유

운영 수동 TIDAL 작업은 `pending`이고 시작 샘플 1건뿐이었다. 별도 MusicBrainz 스냅샷 작업은 `running`으로 25,395개 후보를 처리 중이었다. 화면은 최신 수동 작업의 상태·샘플만 표시하면서 전체 활성곡 증가를 수동 작업의 증가량으로 계산해, 상태와 그래프가 서로 다른 작업을 가리켰다. 워커는 진행 중인 스냅샷 작업을 마친 뒤 수동 작업을 시작한다.

## 변경

- 관리자 API가 현재 실행 중인 EMS 작업의 원천·상태·후보·처리·매칭·대기 수를 반환한다. 최신 수동 TIDAL 작업은 별도 필드로 유지한다.
- 전체 활성곡 그래프는 활성곡의 `first_seen_at`, 현재 작업 그래프는 후보의 `created_at`과 `resolved_at`으로 최근 12시간 누적 추이를 만든다. 화면을 다시 열어도 DB에서 복원된다.
- 상태 카드에 현재 작업 원천과 처리율을 표시한다. MusicBrainz 작업 중 수동 작업이 `pending`이면 대기 이유를 알리고, 버튼은 `수동 수집 예약`으로 표시한다. 전체 유입량을 수동 작업 성과로 표시하지 않는다.
- 이력 조회가 실패해도 현재 수집 현황은 독립 갱신한다. 기존 시작·일시정지·재개 API와 권한은 변경하지 않았다.

## 검증

- 운영 DB에서 수동 작업 `pending`·샘플 1건, MusicBrainz 작업 `running`·후보 25,395건을 확인했다. `first_seen_at`·`resolved_at`의 실제 데이터와 집계 SQL 결과를 확인했다.
- Admin/Web `npm run build`: 통과. Admin 기존 큰 번들 경고, Web 로컬 Auth0 환경 변수 경고는 남아 있다.
- 수정한 Admin/Web 파일 ESLint: 오류 0.
- `git diff --check`: 통과.
- 자동 테스트는 요청되지 않아 추가하거나 실행하지 않았다.

## 운영 적용과 남은 확인

- Web 이미지를 배포한 뒤 관리자 화면에서 현재 작업·대기 작업과 두 그래프, 공개 readiness를 확인한다.
